3. attributes
4. nesting rules

```text

:::
```

```text

```

# IMPORTANT IMPLEMENTATION PRINCIPLES
 
Follow these principles throughout the implementation.
 
## DO NOT OVER-ENGINEER
 
Do not build:
 
- a full replacement for Notion
- a full replacement for draw.io
- a full WYSIWYG office suite
- an arbitrary HTML execution system
- a complete graphics design application
Build what Memoria actually needs.
 
---
 
# DO NOT ALLOW UNSAFE RAW HTML
 
Maintain the existing security model.
 
Do not solve custom rendering by enabling arbitrary HTML execution.
 
All MMD components must render through controlled React components.
 
---
 
# PRESERVE EXISTING CONTENT
 
Never require users to manually convert existing notes.
 
Existing Markdown must remain valid.
 
---
 
# KEEP AI OUTPUT DETERMINISTIC
 
AI prompts must include the exact supported syntax.
 
Do not tell AI to:
 
> "use rich formatting"
 
without defining what that means.
 
The MMD specification should be the source of truth.
 
---
 
# AVOID AI HALLUCINATED SYNTAX
 
The AI prompt should include only supported MMD components.
 
Provide a concise syntax reference to the AI.
 
Do not include experimental syntax in production prompts.
 
---
 
# DO NOT AUTOMATICALLY OVERDECORATE DOCUMENTS
 
AI should not turn every paragraph into:
 
- a card
- a callout
- a custom section
- an image
Use enhanced elements only when they improve comprehension.
 
A normal well-structured Markdown document should still be a valid and desirable result.
 
---
 
# ACCESSIBILITY
 
All MMD components must consider accessibility.
 
At minimum:
 
- images require meaningful alt text
- interactive details should be keyboard accessible
- diagrams should have a descriptive label/caption
- buttons must have accessible labels
- sufficient text readability
- semantic HTML where appropriate
- keyboard navigation for important editor functions
Do not sacrifice accessibility for visual design.
 
---
 
# RESPONSIVE DESIGN
 
All rendered MMD content must work on:
 
- desktop
- tablet
- mobile
Pay special attention to:
 
- columns
- galleries
- diagrams
- images
- tables
- code blocks
- callouts
- cards
Columns should stack on smaller screens.
 
Images must not overflow their container.
 
Diagrams must scale appropriately.
 
---
 
# PERFORMANCE
 
Do not allow large documents to become unnecessarily slow.
 
Consider:
 
- memoized rendering
- lazy loading images
- lazy loading diagrams
- efficient parsing
- avoiding repeated parsing of unchanged content
- efficient editor state management
Do not prematurely optimize.
 
Measure or identify actual bottlenecks before introducing complicated optimizations.
 
---
 
# SECURITY
 
Treat all user-authored and AI-generated MMD as untrusted content.
 
Prevent:
 
- XSS
- unsafe HTML
- unsafe URLs
- executable attributes
- malicious SVG behavior where applicable
- arbitrary script execution
Validate external image URLs according to the existing security model.
 
Do not blindly trust AI-generated content.

Use normal Markdown for ordinary document structure.

Do not use HTML.
 
Do not invent custom block types.
 
Supported blocks:
[list the supported production blocks]

Do not add decorative images.

Use meaningful alt text for images.
 
Use diagrams when a visual structure, relationship, flow, architecture, or process would significantly improve understanding.

If:
 
```text

```
 
use an image or diagram mechanism.
 
If:
 
```text
NO
```
 
use normal text/MMD.
 
Do not generate visual content merely because the system supports it.

Use a diagram when the content contains relationships such as:

- a simple list is enough

# MILESTONE 13 — USER AI WORKFLOW
 
Memoria should support users who do not have a built-in AI provider.
 
The application should be able to generate a ready-to-copy AI prompt.
 
The workflow should be:
 
```text
User chooses content generation
        ↓
Memoria generates MMD-aware AI prompt
        ↓
User copies prompt
        ↓
User sends it to external AI
        ↓
AI returns one Markdown code block
        ↓
User copies result
        ↓
User pastes into Memoria
        ↓
Memoria detects outer code fence
        ↓
Memoria safely extracts document
        ↓
MMD parser processes document
        ↓
Preview renders rich content
```
 
Make this workflow easy to understand.

# END GOAL
 
The final Memoria system should feel like a polished educational document editor built around Markdown.
 
A user should be able to write something as simple as:
 
```markdown
# Network Layer
 
The Network Layer handles communication between different networks.
```
 
but also create a rich document such as:
 
```text
# Network Layer
 
:::summary
The Network Layer enables packet delivery between different networks.
:::
 
:::definition{term="Routing"}
The process of selecting a path for packets to travel across a network.
:::
 
:::diagram{id="network-topology" caption="Basic Network Topology"}
:::
 
:::warning{title="Important"}
Routers use routing information to determine where packets should be forwarded.
:::
 
:::example{title="Example"}
A packet traveling from one network to another may pass through multiple routers.
:::
 
:::details{title="Additional Explanation"}
Additional technical information can be placed here without cluttering the main document.
:::
```
 
The same content should:
 
- remain text-based
- be editable
- be copyable
- be AI-generatable
- be rendered beautifully
- support images
- support diagrams
- work responsively
- export to PDF
- export to DOCX
- remain compatible with existing Memoria content
The final result should be **Memoria Markdown**, not simply "Markdown with random custom syntax."
 
Treat MMD as a properly designed, documented, versioned content format that is integrated throughout the entire Memoria system.
